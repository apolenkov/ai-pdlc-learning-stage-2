# Описание учебного MR R2

Заголовок: `Уточнить сброс формы кредитного калькулятора`.

Добавьте ссылку на вашу личную учебную задачу Jira — выданную вам или созданную по [канонической инструкции R2](https://apolenkov.github.io/customdev-learning/guides/stage-2.html) и [порядку доступа к DEMO](https://apolenkov.github.io/customdev-learning/corporate-resources.html#jira). Не подставляйте случайный ключ.

## Что изменено

В личной ветке R1 из исходного baseline этого репозитория согласовано правило очистки предыдущего результата при ошибке. В новом diff R2 добавлено только требование сброса: значения `3 000 000 ₽`, `16%`, `240 месяцев`, отсутствие ошибок и результат «—» без автоматического расчёта. Повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибку. Пять сценариев R1 сохранены; итоговый договор содержит восемь сценариев.

Ссылку на `transfer.md` и фактический полный SHA R1 из Git добавьте, когда нужно подтвердить происхождение позднего старта. Не копируйте в описание выдуманное происхождение или одобрение.

## Проверка автора

Target: `course/<логин>/stage-1-error-result`. Source: `course/<логин>/stage-2-reset`. Перед отправкой прочитайте актуальный diff — вкладку **Changes** в MR или точные команды:

```bash
git diff course/<логин>/stage-1-error-result...HEAD --check
git diff course/<логин>/stage-1-error-result...HEAD -- specification.md transfer.md
```

Запишите фактический результат. Программа, Node.js и OpenSpec на этой ступени не запускались.

## Отметки по текущему diff

Для версии нужны три отдельные отметки: руководителя проекта — что цель и ожидаемый результат соответствуют запросу; аналитика — что требования полны и понятны; технического руководителя — что решение реализуемо и проверки достаточны. Если изменение затрагивает архитектуру или остаётся архитектурный спор, требуется четвёртая отметка архитектора.

### Проверка аналитика

- Сохранены ли правило и все пять сценариев R1?
- Полностью ли определены значения, ошибки и результат? Указано ли, что повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибку?
- Согласованы ли правило, три новых сценария и раздел открытых вопросов?
- Подтверждает ли `transfer.md` фактический baseline позднего старта?

### Проверка технического руководителя

- Можно ли однозначно реализовать сброс без скрытых решений?
- Достаточно ли входных данных и ожидаемых результатов для будущих тестов?
- Есть ли решение, которое нужно вернуть аналитику до реализации?

### Архитектурная проверка, когда нужна

- Меняет ли решение границы систем, хранение данных, безопасность или значимое взаимодействие компонентов?
- Если да, зафиксировал ли архитектор свою отметку по этому diff?

Review выполняются последовательно на Git-платформе и относятся к текущему source. Этот файл содержит вопросы, а не заранее выданные подтверждения.

После необходимых отметок можно запросить необязательную [помощь ИИ](../ai/request.md). Принятые предложения остаются в текущей ветке; если diff изменился, нужные отметки получают заново. Затем смёржьте MR только в личную base-ветку своего fork, не в общую `main`, и продолжите по [маршруту курса](../README.md#дальше-по-курсу). Отдельные AI-ветки не требуются.
