# Описание учебного PR шага 2

На GitHub краткая форма подставляется в PR автоматически из `.github/pull_request_template.md`. В GitLab шаблона нет: скопируйте текст из `.github/pull_request_template.md` в описание MR. Этот файл — полные вопросы ревьюерам.

Заголовок: `Уточнить сброс формы кредитного калькулятора`.

Добавьте ссылку на вашу личную учебную задачу: issue в своём fork или, если курс проходят в компании, задачу в трекере команды. Порядок — на [странице шага 2](https://apolenkov.github.io/ai-pdlc-learning/guides/s2-review.html), доступ в компании — в [корпоративных ресурсах](https://apolenkov.github.io/ai-pdlc-learning/corporate-resources.html#jira). Не подставляйте случайный ключ.

## Что изменено

В личной ветке шага 1 из исходного baseline этого репозитория согласовано правило очистки предыдущего результата при ошибке. В новом diff шага 2 добавлено только требование сброса: значения `3 000 000 ₽`, `16%`, `240 месяцев`, отсутствие ошибок и результат «—» без автоматического расчёта. Повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибку. Пять сценариев шага 1 сохранены; итоговый договор содержит восемь сценариев. В шапке `specification.md` записано: «Архитектурный разбор: не требуется» либо «запрошен (признак)».

Ссылку на `transfer.md` и фактический полный SHA шага 1 из Git добавьте, когда нужно подтвердить происхождение позднего старта. Не копируйте в описание выдуманное происхождение или одобрение.

## Проверка автора

Target: `course/your_login/stage-1-error-result`. Source: `course/your_login/stage-2-reset`. Замените `your_login` своим логином. Перед отправкой прочитайте актуальный diff — вкладку **Changes** в PR или точные команды:

```bash
git diff course/your_login/stage-1-error-result...HEAD --check
git diff course/your_login/stage-1-error-result...HEAD -- specification.md transfer.md
```

Запишите фактический результат. Программа, Node.js и OpenSpec на этой ступени не запускались.

## Одобрение по текущему diff

Одобрение даёт владелец продукта: он подтверждает, что цель и ожидаемый результат соответствуют запросу, и нажимает Approve. Аналитик и техлид оставляют замечания в PR. Архитектора приглашают через @, если изменение затрагивает данные, интеграции, безопасность или производительность, либо при споре; он пишет замечания (и `design.md`), но одобряет по-прежнему владелец продукта. После новых коммитов владелец продукта одобряет последнюю версию заново. Автор не одобряет свой запрос; ИИ и автоматическая проверка одобрение не заменяют.

### Вопросы аналитику

- Сохранены ли правило и все пять сценариев шага 1?
- Полностью ли определены значения, ошибки и результат? Указано ли, что повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибку?
- Согласованы ли правило, три новых сценария и раздел открытых вопросов?
- Подтверждает ли `transfer.md` фактический baseline позднего старта?
- Записан ли в шапке `specification.md` архитектурный разбор: «не требуется» либо «запрошен (признак)» с названием признака?

### Вопросы техлиду

- Можно ли однозначно реализовать сброс без скрытых решений?
- Достаточно ли входных данных и ожидаемых результатов для будущих тестов?
- Есть ли решение, которое нужно вернуть аналитику до реализации?

### Когда приглашать архитектора

- Меняет ли решение границы систем, хранение данных, интеграции, безопасность или производительность? Есть ли спор между аналитиком и техлидом?
- Если да, запишите в шапке `specification.md` «Архитектурный разбор: запрошен (признак)», упомяните архитектора через @ в комментарии к PR и назовите признак или спор. Учтите его замечания; одобряет по-прежнему владелец продукта.
- Если нет, запишите «Архитектурный разбор: не требуется». На шаге 3 создайте папку изменения без `design.md`, причину запишите в `proposal.md`.

### Чек-лист одобрения

- [ ] Аналитик и техлид оставили замечания, все обсуждения решены.
- [ ] Архитектор приглашён через @, если есть признак (данные, интеграции, безопасность, производительность) или спор; иначе «не требуется».
- [ ] Владелец продукта одобрил последнюю версию (Approve после последнего коммита).

Review выполняются на Git-платформе и относятся к текущему source. Этот файл содержит вопросы, а не заранее выданные подтверждения.

После одобрения можно запросить необязательную [помощь ИИ](../ai/request.md). Принятые предложения остаются в текущей ветке; после новых коммитов владелец продукта одобряет последнюю версию заново. Затем смёржьте PR только в личную base-ветку своего fork, не в общую `main`, и продолжите по [маршруту курса](../README.md#дальше-по-курсу). Отдельные AI-ветки не требуются.
