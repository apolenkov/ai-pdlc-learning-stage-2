# Правила отдельного шага 2: поздний старт

- Этот репозиторий предназначен только для позднего старта. Ученик, уже завершивший шаг 1, не переходит сюда: он продолжает в своей текущей папке и ветке.
- Место в курсе: шаг 1 «Требования в Git» → шаг 2 «Проверяем и согласуем» → обязательный шаг 3 «Изменение в OpenSpec» → шаги 4–5. Поздний старт выполняет шаги 1 и 2 в этом checkout: `course/<логин>/stage-1-error-result` → `course/<логин>/stage-2-reset`. Не клонируйте R1 рядом и не переносите готовое решение из другого эталона.
- До шага 1 ученик разбирает исходное обращение, заполняет общий шаблон и формирует один intent. Он развивается на шагах 1–3; отдельное намерение и новая папка для каждого шага не создаются.
- `specification.md` в общей `main` — исходное состояние с открытым вопросом, а не готовое решение ученика. Сначала внесите шаг 1 в личной ветке и зафиксируйте фактическое происхождение в `transfer.md`.
- Перед clone создайте fork на GitHub (в GitLab — проект через **New project → Import project → Repository by URL**) и клонируйте URL своего fork. В локальном checkout `origin` указывает на ваш fork; второй remote для обычного учебного маршрута не нужен.
- PR шага 2 (в GitLab — MR) сравнивает source `course/<логин>/stage-2-reset` с личным target `course/<логин>/stage-1-error-result`, не с общей `main`. Одобрение по текущему diff даёт владелец продукта: он нажимает Approve. Аналитик и техлид оставляют замечания в PR. Архитектора приглашают через @, если изменение затрагивает данные, интеграции, безопасность или производительность, либо при споре; он пишет замечания (и `design.md`), но одобряет по-прежнему владелец продукта. После новых коммитов владелец продукта одобряет последнюю версию заново. Автор не одобряет свой запрос; ИИ и автоматическая проверка одобрение не заменяют. После одобрения PR можно смёржить в личную base-ветку fork, но не в общую `main`; force push и обход защиты запрещены.
- Шаг 2 определяет три сценария сброса. Повторный сброс не меняет состояние, не запускает расчёт и не показывает ошибку.
- Шаг 2 обязательно включает commit, push, PR и одобрение владельца продукта по текущему diff. Если используете необязательную помощь ИИ, принятые предложения сохраняются в той же ветке; для изменённого diff владелец продукта одобряет новую версию заново. Отдельные AI-ветки и упражнения не нужны.
- На шагах 1 и 2 меняйте только Markdown-договор и учебные документы. Не добавляйте Node.js, OpenSpec, npm-инструменты или код приложения.
- Обязательный шаг 3 можно выполнить в этой папке от принятой ветки `course/<логин>/stage-2-reset`; обновите правила под шаг 3 и следуйте native OpenSpec-инструкции. Не клонируйте сервисный пример, не запускайте Apply и не отмечайте задачи реализации выполненными.
- Проверяйте актуальный diff и фактическое состояние Git; полный SHA фиксируйте только там, где он нужен для происхождения или передачи. При грязном дереве, неверном источнике, неизвестной учебной задаче (issue в своём fork или задача в трекере команды) или нехватке прав остановитесь; не подменяйте факты и одобрения.
- Не сохраняйте секреты, токены, персональные данные и корпоративные документы в Git, сообщениях агенту или URL.

Сопровождение эталона владельцем в отдельной maintenance-ветке не является учебным прохождением и регулируется задачей сопровождения.
